# 业务规则

## 一、目标业务规则

### 1. 角色与数据范围

角色枚举以 `prisma/schema.prisma` 的 `Role` 为准。

| 枚举 | 中文名称 | 目标职责 |
|------|----------|----------|
| `ADMIN` | 系统管理员 | 系统配置、用户和部门管理、全局查看 |
| `SUPERVISOR` | 督办管理员 | 督办跟踪、统计导出、全局查看 |
| `DEPARTMENT_MANAGER` | 部门事项管理岗 / 部门督办管理员 / 系统办理人 | 代表部门填报、办理、提交材料 |
| `DEPARTMENT_LEADER` | 部门领导 | 查看本部门相关事项、进行部门级审批或办理 |
| `VICE_PRESIDENT` | 公司主管领导 | 查看本人提出、本人分管、当前审批或明确授权范围内事项 |
| `PRESIDENT` | 公司主要领导 | 查看本人提出、当前审批、需主要领导决策事项；是否全局查看需明确授权 |

目标数据范围：

1. `ADMIN`、`SUPERVISOR`：全局查看。
2. `VICE_PRESIDENT`：默认查看本人提出、本人分管、当前审批、明确授权范围内事项，不默认全局。
3. `PRESIDENT`：至少可查看本人提出、当前审批、需主要领导决策事项；是否全局查看需明确授权。
4. `DEPARTMENT_LEADER`、`DEPARTMENT_MANAGER`：查看本部门主责或配合相关事项，不按 `creatorId` / `firstSubmitterId` 限制查看。

### 2. 系统用户与业务责任人

**系统用户**（`User`）是登录账号，用于登录、审批、办理、上传、权限判断和流程审计。关键系统用户角色包括：事项创建人、首次提交人、当前审批人。

**业务责任人**是姓名文本，用于事项展示、留痕和导入导出，不一定登录系统，不参与权限判断。

权限判断原则：

1. 查询统计按组织权限（部门主责和配合范围）。
2. 审批按当前审批节点判断。
3. 办理按业务动作判断：待分解由主责部门角色办理，草稿/退回修改/进行中提交由事项办理人办理。
4. 核心内容修改必须走调整审批。
5. 业务责任人姓名不参与权限判断。

### 关键系统用户字段补充

| 字段 | 权限语义 |
|------|----------|
| `responsibleLeaderUserId` | 责任领导系统用户，FK → users。责任领导语义字段，不默认办理；本次不新增本人可见条件 |
| `responsiblePersonUserId` | 责任人系统用户，FK → users。IN_PROGRESS 后为唯一办理人 |

### 3. 业务责任人与部门字段

每条事项都有业务责任人信息，用于展示、留痕和导入导出，**不参与系统权限判断**。

重点工作、主要工作：
- 责任领导（姓名文本）和责任人（姓名文本），记录实际业务负责人。

待办事项：
- 唯一主责部门，配合方列表（可多个），每方可填配合领导和配合人员（均为姓名文本）。
- 配合部门参与事项可见范围，不计入完成率。

姓名文本字段不产生审批、办理或可见权限。权限判断始终依赖系统用户字段和部门角色。

### 4. 工作事项、工作节点与年度

重点工作、主要工作中，一条系统 `WorkItem` 记录代表一个可独立执行、调整、提交材料和审批的**工作节点**；不新增父事项实体或父级审批流。

1. 同一业务工作事项下的节点，以 `assessmentYear + type + normalizedWorkItem` 临时分组；它仅用于展示、精确筛选和允许的批量操作，不是长期稳定业务 ID。
2. `workItem` 的业务文案为“工作事项”，`workNode` 的业务文案为“工作节点”。重点/主要工作的新建、结构化编辑和 Excel 导入必须同时填写两者；标题由服务端生成 `工作事项｜工作节点`，仅作展示，禁止反向解析作为业务依据。历史 `nodes` 树状字段在界面中统一称为“任务分解节点”，不与 `workNode` 混用。
3. 历史记录未填写工作节点时维持原样展示；仅编辑普通字段不要求补录。编辑工作事项或工作节点后，该记录进入结构化维护模式，两个字段均为必填。
4. `assessmentYear` 是考核年度，不从创建时间或计划完成时间推断。新建、导入和结构化调整均必须明确年度；同名工作事项跨年度不是同一分组。
5. 修改单一节点的工作事项名称只会移动该节点所属分组，不会同步修改其他节点；界面必须明确提示这一点。
6. 重点、主要工作支持单条新增或批量新增工作节点。批量新增的组头统一确定年度、类型和工作事项；每行独立填写工作节点及责任信息，服务端一次校验并在一个事务内创建草稿。
7. 已有工作事项候选只能按当前用户可见范围返回；部门用户默认按本部门主责范围筛选，候选中的节点数量只表示当前用户可见的节点。
8. 选择已有工作事项时，若其当前可见节点的业务类别或是否创新工作属性一致，系统可自动带入作为新节点的初始值；属性不一致时不得推断或覆盖表单值，必须提示用户确认。该带入不修改已有节点。

### 5. 事项状态

事项在生命周期中经历以下状态：

| 分类 | 状态 | 业务含义 |
|------|------|----------|
| 稳定业务态 | 草稿 | 新建或被退回待修改的事项 |
| 稳定业务态 | 待分解 | 公司领导发起的待办事项，等待部门分解方案 |
| 稳定业务态 | 进行中 | 已立项通过，正在执行 |
| 稳定业务态 | 已完成 | 事项办结 |
| 稳定业务态 | 已取消 | 事项终止 |
| 审批过程态 | 立项审批中 | 提交立项或分解方案，等待审批 |
| 审批过程态 | 调整审批中 | 进行中事项申请调整核心内容，等待审批 |
| 审批过程态 | 取消审批中 | 进行中事项申请取消，等待审批 |
| 审批过程态 | 完成审批中 | 进行中事项提交完成材料，等待审批 |

业务流转要点：

1. 审批通过后事项直接进入"进行中"，不经过中间态。
2. 审批退回到"草稿"或"待分解"（取决于退回前状态），退回痕迹在事项上保留。
3. "退回待修改"不是独立状态，而是草稿+退回痕迹的派生展示。
4. 完成审批和取消审批各自统一为一个审批态，不再区分部门级和公司级。
5. 公司领导取消审批在"取消审批中"状态下通过审批节点区分，不单独设状态。

完整技术设计见 `docs/design/状态机设计.md`。

### 6. 审批流转规则

审批分为四种：**立项审批**、**调整审批**、**取消审批**、**完成审批**。

**进入审批**：事项提交审批时，系统记录审批前的业务状态和审批类型，事项进入对应的审批态，指派第一审批节点。

**审批通过**：
- 如果还有下一审批节点，事项保持在当前审批态，仅切换到下一审批人。
- 如果所有节点审批通过，事项进入目标业务状态（立项→进行中，调整→进行中，取消→已取消，完成→已完成）。

**审批退回**：事项恢复到审批前的业务状态，退回原因保留在事项上。

**退回路径**：退回恢复到哪个状态取决于审批前记录的状态，不由事项类型或布尔标记决定。普通事项退回到草稿，公司领导发起的待办事项退回到待分解。

**批量提交 / 批量审批**：只支持重点、主要工作在同一工作事项分组内的工作节点；批量提交仅限草稿，批量审批仅限立项审批。服务端在预检和执行时均校验权限、状态、`updatedAt` 版本与下一路由；不同路由不能混批，执行使用一个事务，任一节点失败则整批不生效。退回、完成、调整和取消不提供批量操作。

技术实现见 `docs/design/状态机设计.md`。

### 7. 审批与办理口径

**待我处理 = 待审批 + 待办理。**

**待审批**：当前用户是事项的当前审批人。部门级审批还需匹配主责部门范围。

**待办理**：不需要审批但需要当前用户推进的事项，具体包括：
- 草稿：仅事项创建人可编辑提交（退回草稿由首次提交人处理，部门其他人不能因同部门而代处理）。
- 待分解：仅主责部门的部门级角色可办理，配合部门不默认计入。
- 审批退回后进行中：由 `responsiblePersonUserId` 办理（与正常 IN_PROGRESS 操作权一致），普通进行中事项不进入待办理。
- 进行中事项的调整、取消、完成提交由 `responsiblePersonUserId` 操作；
  `creatorId` / `firstSubmitterId` 在审批通过后不再产生办理权。

配合部门可见不等于待办理。全局查看权限不产生待办理。业务责任人姓名不产生办理权限。

### 8. 目标统计口径

1. 首页统计卡片必须与点击后的列表结果一致。
2. `待审批`、`待办理`、`待我处理` 的统计条件必须与对应列表查询条件一致。
3. 超期、进行中、已完成等状态统计必须使用统一状态集合。
4. TODO 多主责部门完成率按主责部门计入；配合部门不计入完成率分母和分子。
5. 统计涉及主责部门时必须通过统一 helper 或统一权限模块读取主责部门集合。
6. Dashboard 的概览卡片、状态数量、完成率，以及 Dashboard 内嵌的到期提醒和处理中心轻量列表，统一按用户选择的 `assessmentYear` 计算；首页数量跳转到事项列表或状态列表时必须携带相同年度，保证数量与列表一致。
7. 独立到期提醒页和独立处理中心默认保持跨年度口径，以免遗漏其他年度仍需关注或处理的事项；它们不继承 Dashboard 的年度筛选。
8. 三类事项列表和 Dashboard 状态数量对应的 `/status` 列表默认按系统默认管理年度查询，并提供年度切换和“全部年度”选项；年度切换必须进入服务端查询并同步到 URL，月份筛选保留为当前已返回年度数据上的前端过滤。系统设置缺失或读取失败时安全回退当前自然年；“全部年度”使用显式参数，不得被默认年度覆盖。
9. 年度查询页面初始化优先级为：有效 URL 年度、当前用户本机保存的有效查询年度、系统默认管理年度、当前自然年。个人偏好仅用于 Dashboard、三类事项列表和状态列表，不用于新建、批量新建、导入、编辑或任何服务端写操作；“全部年度”不保存为个人偏好。

### 9. Dashboard API

首页已统一调用，并通过 `year` 指定考核年度：

```http
GET /api/dashboard?year=2026
```

首页不再调用 `/api/works` 拉全量事项后在前端计算列表。目标接口一次返回：

1. `summary`：卡片统计。
2. `lists.expiringAndOverdue`：到期提醒轻量列表。
3. `lists.myActionRequired`：处理中心轻量列表。

两组轻量列表与 `summary` 使用同一个 `assessmentYear`，只返回首页需要字段，不返回完整 `WorkItem`。独立 `/alert`、`/process` 页面仍通过事项查询接口按跨年度口径获取数据。

### 10. API 和服务端约束

1. 创建、更新、删除、审批、提交材料、导入导出等关键接口必须校验登录态。
2. 涉及部门数据时必须校验数据范围。
3. 涉及审批时必须校验当前审批人。
4. 涉及状态变化时必须校验当前状态是否允许该动作。
5. 不允许通过普通更新接口绕过 workflow 修改状态、当前审批人或审批辅助字段。
6. 核心内容修改必须走 `ADJUSTING`。

### 11. 附件与证明材料

1. 附件查看应与事项查看权限保持一致。
2. 附件上传应与事项办理权限或当前动作权限保持一致。
3. 上传人可以删除自己上传的附件。
4. `ADMIN` / `SUPERVISOR` 可按管理口径查看和删除附件。
5. 业务责任人姓名字段不产生附件查看、上传或删除权限。

涉及以下任一内容时，PR 必须说明影响角色、影响页面、影响接口、自测角色和状态流转前后变化：

1. `Role`、`WorkItemStatus`、`WorkItemType`、`ApprovalType`。
2. `src/lib/workflow.ts`。
3. 权限、数据范围、附件权限、Dashboard 统计。
4. `/api/works/**`、`/api/dashboard/**`、`/api/excel/**`、`/api/upload`、`/api/attachments/**`。
5. 首页统计、审批中心、事项列表、事项详情。
6. `creatorId`、`firstSubmitterId`、`currentApproverId`、`currentApproverRole`。
7. `responsibleLeader`、`responsiblePerson`、`responsiblePersons`、`cooperatePersons` 的语义或导入导出格式。
