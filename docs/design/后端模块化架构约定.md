# 后端模块化架构约定

## 一、架构定位

本项目为基于 **Next.js 全栈单体应用** 的公司督办管理系统，当前不采用传统意义上的前后端物理分离结构，也不机械套用教科书式 Clean Architecture。

本项目采用：

> **Modular Monolith + Feature-based Layered Architecture 简化方案**

即：

```txt
第一层：按业务功能模块划分；
第二层：每个业务模块内部按职责分层；
第三层：保留 Next.js 现有 app/api 与 app/(app) 入口结构。
```

本次架构治理的目标不是重写系统，而是在不改变现有接口路径、业务行为和数据库结构的前提下，逐步解决当前代码中存在的：

```txt
1. API Route 过厚；
2. src/lib 职责过杂；
3. 权限、状态、审批流规则分散；
4. Prisma 查询散落；
5. 类型定义、DTO、接口返回结构难找；
6. 前端 API 调用、UI 展示、后端业务逻辑混杂。
```

## 三、为什么不采用 src/backend + src/frontend

本项目当前是 Next.js 全栈单体，不是传统的：

```txt
后端：.NET Web API / Spring Boot
前端：Vue / React
```

因此当前阶段不采用：

```txt
src/backend/
src/frontend/
```

这种顶层前后端物理分离方式。

原因：

```txt
1. Next.js 的 app/api 和 app/(app) 本身就是框架约定；
2. 当前主要问题不是前后端没分离，而是业务模块边界不清；
3. 许多业务类型、状态枚举、DTO、展示名称存在前后端共用需求；
4. 过早前后端物理拆分会增加路径复杂度；
5. 当前更适合先在单体内部建立清晰模块边界。
```

后续如果确有需要拆成独立前后端工程，可在当前模块化结构稳定后，再按：

```txt
features/*/application + infrastructure → 后端项目
features/*/client + ui                  → 前端项目
features/*/domain                       → 共享类型包或分别复制
```

进行演进。

## 四、feature 模块划分原则

业务代码优先按功能模块划分，而不是按技术类型划分。

推荐模块包括：

```txt
works           事项模块，包含重点工作、主要工作、待办事项的基础业务；
workflow        审批流模块，包含提交、审批、驳回、完成、调整、取消、分解；
attachments     附件模块，包含证明材料上传、下载、删除、权限；
excel           Excel 模块，包含导入、导出、模板、完成率导出；
dashboard       看板与统计模块；
users           用户、角色、密码、账号管理；
departments     部门组织模块；
operation-logs  操作日志模块。
```

不要新建笼统的大模块，例如：

```txt
services/
repositories/
types/
utils/
```

也不要继续把业务代码堆到：

```txt
src/lib/
```

## 五、每个 feature 内部的五类目录

每个业务模块统一采用并排五个目录：


不再额外增加过深的：

```txt

```

目录层级保持简洁，方便查找和维护。

# 1. domain

## 职责

`domain` 放当前模块的核心业务语言和业务规则。

包括：

```txt
业务类型
枚举
状态定义
状态判断
业务规则
权限规则
状态流转规则
模块内常量
```

示例：

```txt
features/works/domain/
  work.types.ts
  work-status.ts
  work-status.rules.ts
  work.rules.ts
  work.permissions.ts
  work.visibility-policy.ts
```

## 约定

`domain` 应尽量保持纯净：

```txt
尽量不直接访问 Prisma；
尽量不读取 cookies；
尽量不依赖 NextResponse；
尽量不直接操作 fs；
尽量不写 React 组件；
尽量不写 UI 样式。
```

允许前端、后端、UI 共用其中的纯类型、枚举、状态名称、状态判断函数。

例如：

```txt
WorkStatus
WorkType
WORK_STATUS_LABELS
isCompletedStatus
isApprovalStatus
getWorkTypeLabel
```

## server-only 规则

由于本项目采用简化目录结构，不再单独拆 `server/domain`。

如果某些 domain 文件只适合服务端使用，应通过文件命名明确标识：

```txt
*.server-permissions.ts
*.server-policy.ts
*.prisma-policy.ts
*.visibility-policy.ts
```

例如：

```txt
work.server-permissions.ts
work.visibility-policy.ts
```

这类文件不得被 `client` 和 `ui` 引用。

它负责组织一次完整业务操作。

包括：

```txt

审批驳回
提交完成申请
提交调整申请
提交取消申请

```

示例：

```txt
features/works/application/
  query-works.usecase.ts
  get-work-detail.usecase.ts
  create-work.usecase.ts
  update-work.usecase.ts

```

```txt
features/workflow/application/
  submit-for-approval.usecase.ts
  approve-work.usecase.ts
  reject-work.usecase.ts
  submit-completion.usecase.ts
  submit-adjustment.usecase.ts
  submit-cancel.usecase.ts
```

## application 做什么

```txt
1. 接收 route 传入的参数；
2. 调用 domain 规则判断业务是否合法；
3. 调用 infrastructure 查询或保存数据；
4. 调用 operation log 记录操作；
5. 必要时组织数据库事务；
6. 返回 DTO 或响应结果。
```

## application 不做什么

```txt
不直接写 HTTP Response；
不直接读取 cookies；
不直接写 React 组件；
不直接拼复杂 UI 文案；
不直接把 Prisma 原始对象暴露给前端。
```

# 3. infrastructure

## 职责

`infrastructure` 放技术实现。

包括：

```txt
Prisma repository
Prisma query builder
数据库 mapper
Excel 读写
文件存储
本地磁盘存储
MinIO/S3 存储适配
外部系统调用
```

示例：

```txt
features/works/infrastructure/
  work.repository.ts
  work.query-builder.ts
  work.mapper.ts
```

```txt
features/excel/infrastructure/
  xlsx-reader.ts
  xlsx-writer.ts
  work-import-parser.ts
  work-exporter.ts
  completion-rate-exporter.ts
```

```txt
features/attachments/infrastructure/
  attachment.repository.ts
  local-file-storage.ts
```

## 约定

```txt
1. Prisma 查询优先放在 repository；
2. route.ts 不应直接写复杂 Prisma 查询；
3. application 层通过 repository 获取数据；
4. Excel、文件、外部服务等技术细节不进入 domain；
5. infrastructure 不应依赖 ui。
```

### Repository 与表归属规则

**核心原则：模块按业务能力和用例内聚，不按数据库表机械归属。**

允许某个 feature 的 infrastructure 查询支撑本 feature 用例所需的关联表，但须满足以下边界：

1. **查询目的必须服务于本 feature 的用例**，不能变成通用跨模块数据服务。
2. **不能把其他模块的复杂业务规则搬进来**。users 可以校验 department 是否存在，但不应实现 departments 模块的组织树管理规则。
3. **查询返回形状应贴合本 feature 的 use case**，避免为了"表归属纯洁"把大量专用筛选/DTO 拼装塞进别的模块 repository。
4. **跨表访问尽量是只读校验、关联展示、选项查询**；写操作和核心状态变更仍应谨慎，优先由归属模块封装。
5. **复用再提升**：如果同一个跨模块查询开始被多个 feature 复用，再考虑提升到归属模块 repository 或 shared query，而不是一开始就抽。

示例：

| 场景 | 查询 | 放置位置 | 符合哪条 |
|------|------|----------|----------|
| users 创建/更新用户时校验部门存在 | `findDepartmentById(id)` | `users/infrastructure/user.repository.ts` | 只读校验，服务于 users 用例 |
| workflow 分配审批人时查公司领导 | `findPresident()` | `workflow/infrastructure/workflow.repository.ts` | 选项查询，服务于 workflow 用例 |
| excel 导入时查业务部门列表 | `findDepartmentsForImport()` | `excel/infrastructure/work-import.repository.ts` | 关联展示，服务于 excel 用例 |

反例（不允许）：

- `works/infrastructure/` 实现部门组织树遍历 → 这是 departments 的业务规则，不应搬入
- 通用的 `findDepartmentWithFullTree()` 同时被 3 个模块使用 → 应提升到 `departments/infrastructure/` 或 shared

# 4. application 类型约定（原 presentation 已取消）

## usecase 专属类型

仅被一个 usecase 使用、且不作为 HTTP API 契约暴露给 client 的类型，直接定义在对应 usecase 文件顶部，不单独建 DTO 文件。

usecase 内部类型按 CQ 命名：

- 写操作入参使用 `Command` 结尾，例如 `CreateWorkCommand`。
- 读操作入参使用 `Query` 结尾，例如 `WorkListQuery`。
- usecase 返回控制流使用 `Result` 结尾，例如 `CreateWorkResult`。
- 不再用 `Request` / `Response` 命名 usecase 内部类型，避免和 HTTP 层契约混淆。

### usecase Result 类型约定

usecase 的返回控制流使用 `src/shared/result.ts` 提供的共享 `Result<T>` 类型，不要在每个 usecase 中重复定义形如 `{ kind: 'ok' } | { kind: 'error'; status; message }` 的局部 Result。

- 无返回数据：`Result`（即 `ResultOk<void> | ResultError`）
- 有返回数据：`Result<T>`（即 `ResultOk<T> | ResultError`）
- 只有存在额外分支字段、特殊业务语义或复杂控制流时，才允许定义局部 `XxxResult`

`Result` 只表达 usecase 控制流，不直接作为 HTTP body 暴露。route 负责将 `Result` 映射为 HTTP status + JSON body（通过 `ok()` / `fail()` / `fromError()` 等 shared HTTP helper）。

## 多 usecase 共用的 application 类型

被多个 usecase 或 application 层文件复用的类型，放在对应 feature 的 `application/` 下：

```txt
features/works/application/
  work-display.utils.ts     ← 节点展示、调整历史处理（多 usecase 共用）
```

### API DTO、Result 与转换函数规则

HTTP route/controller 的 request / response 类型属于 API 契约。只要 client 会直接发送或接收该 JSON 形状，就放在对应 feature 的 `contract/` 下：

```txt
features/works/contract/
  work-api.types.ts         ← WorkApiDto, CreateWorkRequest, UpdateWorkResponse
```

命名约定：

- route/controller 接收的 JSON body：`XxxRequest`
- route/controller 返回的 JSON body：`XxxResponse`
- request/response 同形或被多个接口复用的实体 DTO：`XxxApiDto`
- API 错误响应：统一使用 shared HTTP 错误类型，不为每个模块新增 `XxxApiErrorDto`

#### contract 层适度原则

contract 层用于表达真实 HTTP JSON 边界，不用于复制 domain、application、client 三套几乎相同的模型。新增或改造 contract 时遵循以下原则：

1. **简单 GET 响应不强制包 envelope**：列表/详情可以直接返回 DTO 或 DTO 数组，例如 `DepartmentListResponse = DepartmentApiDto[]`、`WorkDetailResponse = WorkApiDto`。
2. **只有需要额外元信息时才定义 Response 包装**：分页、导入结果、聚合统计、批量校验结果等可以定义 `XxxResponse` 包含 `items/total/pageSize/errors` 等字段。
3. **mutation/action 按业务语义返回**：创建/更新如果返回资源，直接返回对应 DTO；删除、登出、审批动作等只需表示完成时，可返回 `{ success: true }`。
4. **不把 application Result 原样暴露为 HTTP body**：usecase 可用 `{ kind: 'ok' | 'error' }` 表达控制流，route 负责把它映射为 HTTP status + JSON body。当前项目保持轻量做法：可预期失败可以返回 `{ status, message, code? }`，由 route 通过 shared HTTP helper 统一输出错误 JSON。
5. **避免无意义重导出和空转 mapper**：`client.types.ts` 仅重命名 contract 类型、mapper 仅同字段搬运时，应优先用 `import type`、`type alias`、`Pick/Omit` 或 `satisfies` 简化。
6. **只有发生 JSON 形态变化才写 mapper**：例如 `Date -> ISO string`、隐藏内部字段、relation flatten、不同接口裁剪字段、兼容历史字段等。
7. **request body 的 TS 断言不是运行时校验**：`await request.json() as XxxRequest` 只用于静态类型约束；关键接口应逐步补充 parse/normalize/validate 函数，避免把非法输入误认为已校验。

推荐在 `src/shared/http/` 中维护全局通用响应原语，例如：

```ts
export interface ApiErrorResponse<Code extends string = string> {
  error: string
  code?: Code
  details?: unknown
}

export interface ActionSuccessResponse {
  success: true
}

export interface PageResponse<T> {
  items: T[]
  total: number
  page: number
  pageSize: number
}
```

不要同时定义语义重复的 `ApiErrorDto` / `ApiFailure`。HTTP 层统一使用 `ApiErrorResponse` 表达错误 JSON body；application 层内部的可预期失败继续使用局部 `Result` 类型表达控制流。

`src/shared/http/api-response.ts` 提供 `ok`、`actionOk`、`fail`、`failResult` 等 route 层响应助手。`failResult` 面向当前 usecase 常见的 `{ status, message, code?, details? }` 形态，避免在每个 route 重复拼错误响应；不要为了未来可能的多端适配提前引入额外的错误码到 HTTP status 映射层。

如果 route/controller 的 request/response 与 usecase 的 command/query/result 恰好同形，可以直接复用 contract 中的 API DTO；如果 route/controller 会解析、包装或提取数据后再调用 usecase，则 usecase 的 `Command` / `Query` / `Result` 留在 `application/` 内。

转换函数归属按方向区分：

- repository / Prisma 查询结果 → API DTO：放在 `application/`，例如 `work-api.mapper.ts` 的 `toWorkApiDto`。
- API DTO → 前端 ViewModel，或前端 ViewModel/Patch → API Request DTO：放在 `client/`，例如 `work-view-model.ts`。
- 简单页面模型如果与 API DTO 完全同形，可以在 `client` 中 re-export API DTO，不必额外写 mapper。

理由：

1. DTO 关心的是"API 返回什么形状"，不是领域规则；
2. 转换函数依赖 Prisma include 结构，domain 不应感知 Prisma；
3. route/controller 的 HTTP 契约需要被 client 引用，不能藏在 server-only usecase 文件里；
4. domain 保持纯净：只放枚举、状态判断、业务规则、权限规则，不放 I/O 形状。

## 跨 feature 共用的类型

被多个 feature 引用且属于某个业务模块 API 契约的类型，优先放在该模块的 `contract/` 下，由其他模块通过 `import type` 引用。例如 `works/contract/work-api.types.ts` 可以引用 `attachments/contract/attachment-api.types.ts`。

只有没有明确业务归属、确实是全局通用能力的类型或规则，才提升到根级 `src/shared/`：

```txt
src/shared/completion-rate.rules.ts  ← CompletionRateStat, calculateDepartmentStats
```

## validator / query 解析

Query 参数解析逻辑与 usecase 放在一起（`query-works.usecase.ts` 同时导出 `parseWorkType` / `parseWorkStatusFilter`），route 从 usecase 导入。

## API 响应映射

简单且只被一个 usecase 使用的响应对象映射，可以直接放在 usecase 文件内。

当多个 usecase 返回同一类 API DTO，或需要统一列表、详情、创建、更新的返回口径时，应抽到 `application/<feature>-api.mapper.ts`，集中维护一次映射规则，避免多个小 mapper 漂移。


## 七、app/api 约定

`app/api` 继续作为 Next.js API Route 入口。

但 API Route 应逐步变薄。

目标形态：

```txt
1. 获取当前用户；
2. 解析参数；
3. 调用 application use case；
4. 返回响应。
```

不应继续在 route.ts 中堆积：

```txt
复杂 Prisma 查询
复杂权限判断
状态流转规则
Excel 解析
文件存储细节
大量 DTO 拼装
重复 try/catch
重复登录校验
```

示例：

```ts
// 无动态参数
export const GET = withApiHandler(async (request: NextRequest) => {
  const currentUser = await requireCurrentUser(request)
  const result = await queryWorksUseCase({ currentUser })
  return ok(result)
})

// 有动态参数（内联类型，不定义局部 RouteContext / XxxParams）
export const PUT = withApiHandler(
  async (
    request: NextRequest,
    { params }: { params: Promise<{ id: string }> },
  ) => {
    const currentUser = await requireCurrentUser(request)
    const { id } = await params
    // ...
    return ok(result)
  },
)
```

### withApiHandler 使用规范

1. **所有普通 JSON route 必须使用 `withApiHandler`**，它统一处理 try/catch 和 AppError 转换。
2. **鉴权统一使用 `requireCurrentUser(request)`**，不使用 `verifyToken`、`getUserFromToken`、`getCurrentUserOrAuthError`。
3. **成功响应用 `ok(data)` 或 `success()`**；参数校验失败用 `fail(message, status)`；usecase 可预期失败用 `fromError(result)`。
4. **有动态参数时，handler 第二参数直接内联类型**，不定义局部 `RouteContext` / `XxxParams` 类型：
   ```ts
   // 正确
   async (request, { params }: { params: Promise<{ id: string }> }) => { ... }

   // 错误 — 不要定义局部类型
   type RouteContext = { params: Promise<{ id: string }> }
   async (request, { params }: RouteContext) => { ... }
   ```
5. **文件下载、上传、流式响应、登录、健康检查等特殊接口可以不用 `withApiHandler`**，直接 `export async function`。
6. **`withApiHandler` 内部已处理 `AppError` 和未预期异常**，route 内不需要外层 try/catch。

## 九、src/lib 处理原则

`src/lib` 不立即删除，但要逐步瘦身。

后续不再向 `src/lib` 新增核心业务逻辑。

当前 `src/lib` 中的内容应逐步迁移：

```txt
prisma.ts                  → shared/db/prisma.ts
server-auth.ts             → shared/auth/*
server-permissions.ts      → features/works/domain/*、features/attachments/domain/*
workflow.ts                → features/workflow/*
work-status.ts             → features/works/domain/*
dashboard-data.ts          → features/dashboard/*
excel-utils.ts             → features/excel/*
work-store.ts              → features/works/client/*
attachment-permissions.ts  → features/attachments/domain/*
status-colors.ts           → features/works/ui/*
utils.ts                   → shared/utils、shared/ui、features/works/application
```

迁移时允许保留兼容导出。

例如：

```ts
// src/lib/prisma.ts
export { prisma as default } from '@/shared/db/prisma'
```

或者：

```ts
// src/lib/work-status.ts
export * from '@/features/works/domain/work-status'
export * from '@/features/works/domain/work-status.rules'
```

这样可以避免一次性修改全项目 import。

## 十、依赖方向约定

推荐依赖方向：

```txt
app/api → application
app/api → contract（import type）
application → domain + infrastructure + contract（import type）
infrastructure → shared/db + shared/utils

ui → domain + client
```

尽量避免：

```txt
domain → application
domain → infrastructure
domain → ui
infrastructure → ui
application → ui
client → infrastructure
ui → infrastructure
```

底线原则：

```txt
后端不要依赖 UI；
前端不要依赖 Prisma；
业务规则不要依赖 React；
UI 展示不要承担后端权威权限判断。
```

## 十五、最终目标

本次模块化改造的最终目标是：

```txt
1. 事项规则集中到 works；
2. 审批流规则集中到 workflow；
3. 附件规则集中到 attachments；
4. Excel 导入导出集中到 excel；
5. Dashboard 和完成率口径集中到 dashboard；
6. 用户角色规则集中到 users；
7. API Route 变薄；
8. src/lib 逐步瘦身；
9. Prisma 查询集中；
10. DTO、validator、presenter 有固定位置；
11. 前端 API、ViewModel、UI 组件按模块归位。
```

一句话总结：

> 本项目后续采用 **模块优先、分层适度、路径清晰、渐进迁移** 的架构治理原则。
> 不追求形式上的 Clean Architecture，而追求适合当前 Next.js 全栈单体项目的可维护结构。
