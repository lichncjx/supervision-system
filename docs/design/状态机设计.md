# 状态机设计

## 当前状态口径

当前系统运行态统一为 9 状态：`DRAFT`（草稿）、`PENDING_DECOMPOSE`（待分解）、`PROPOSING`（立项审批中）、`IN_PROGRESS`（进行中）、`ADJUSTING`（调整审批中）、`CANCELLING`（取消审批中）、`COMPLETING`（完成审批中）、`COMPLETED`（已完成）、`CANCELLED`（已取消）。

已取消的历史状态：`APPROVED`（立项通过后直接进入 `IN_PROGRESS`）、`REJECTED`（退回后恢复到 `DRAFT`）、`PENDING_DEPT` / `PENDING_COMPANY`（统一为 `PROPOSING`）、`PENDING_EVIDENCE_DEPT` / `PENDING_EVIDENCE_COMPANY` / `PENDING_COMPLETE`（统一为 `COMPLETING`）、`PENDING_MAIN_LEADER_CANCEL`（在 `CANCELLING` 下通过审批节点区分）。

"退回待修改"不是独立状态，而是 `DRAFT` + 退回痕迹的派生展示和筛选口径。页面、接口状态筛选、Dashboard、处理中心页、Excel 导入导出均按 9 状态口径处理。

## 零、状态元数据

`src/lib/work-status.ts` 当前只维护目标 9 个 `WorkItemStatus` 的展示文案、颜色分组和基础判断。旧状态不再作为当前运行口径。

统一元数据字段包括：

1. `value`：当前代码使用的小写状态值。
2. `prismaValue`：Prisma enum 名称。
3. `label` / `description`：页面、导出和流程记录展示文案。
4. `visualGroup` / `badgeClass`：状态视觉分组和 Badge 样式。
5. `isTerminal`：是否终态，目前仅 `COMPLETED`、`CANCELLED`。
6. `isApproving`：是否处于审批过程。
7. `isHandling`：是否处于业务办理/待处理过程。
8. `isInProgress`：是否沿用当前“进行中”统计/筛选口径。
9. `countsForDeadline`：是否计入临期/超期，`COMPLETED`、`CANCELLED` 不计入。

当前 9 状态元数据口径：

| 状态 | 文案 | 视觉分组 | 终态 | 审批中 | 办理中 | 进行中 | 计入临期/超期 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `DRAFT` | 草稿 | `handling` | 否 | 否 | 是 | 否 | 是 |
| `PENDING_DECOMPOSE` | 待分解 | `handling` | 否 | 否 | 是 | 否 | 是 |
| `PROPOSING` | 立项审批中 | `approving` | 否 | 是 | 否 | 否 | 是 |
| `IN_PROGRESS` | 进行中 | `inProgress` | 否 | 否 | 是 | 是 | 是 |
| `ADJUSTING` | 调整审批中 | `approving` | 否 | 是 | 否 | 否 | 是 |
| `CANCELLING` | 取消审批中 | `approving` | 否 | 是 | 否 | 否 | 是 |
| `COMPLETING` | 完成审批中 | `approving` | 否 | 是 | 否 | 否 | 是 |
| `COMPLETED` | 已完成 | `completed` | 是 | 否 | 否 | 否 | 否 |
| `CANCELLED` | 已取消 | `cancelled` | 是 | 否 | 否 | 否 | 否 |

兼容状态 `pending_approval`、`active`、`decomposed` 已不再作为当前状态元数据维护。

## 一、目标状态集合

### 稳定业务态

| 状态 | 说明 |
| --- | --- |
| `DRAFT` | 草稿/待修改 |
| `PENDING_DECOMPOSE` | 待分解，仅服务于公司领导发起的待办事项 |
| `IN_PROGRESS` | 进行中 |
| `COMPLETED` | 已完成 |
| `CANCELLED` | 已取消 |

### 审批过程态

| 状态 | 说明 |
| --- | --- |
| `PROPOSING` | 立项/分解方案审批中 |
| `ADJUSTING` | 调整审批中 |
| `CANCELLING` | 取消审批中 |
| `COMPLETING` | 完成审批中 |

## 二、状态设计原则

1. `APPROVED` 已取消，审批通过后统一进入 `IN_PROGRESS`。
2. `REJECTED` 已取消，立项审批退回后回到 `DRAFT`，退回痕迹通过退回字段和 workflow record 展示。
3. `PENDING_EVIDENCE_DEPT`、`PENDING_EVIDENCE_COMPANY`、`PENDING_COMPLETE` 已统一为 `COMPLETING`。
4. `PENDING_MAIN_LEADER_CANCEL` 不再单独作为状态，而是在 `CANCELLING` 状态下通过 `currentApproverId`、`currentApproverRole`、`approvalType` 判断当前审批节点。
5. `PENDING_DECOMPOSE` 保留。它不是审批态，而是公司领导发起待办后的业务准备/待分解状态。
6. 任何审批态都必须能通过 `beforeApprovalStatus` 找到退回后的业务状态。

## 三、审批辅助字段

PR 6.1 已在 `WorkItem` 上新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `beforeApprovalStatus` | `WorkItemStatus?` | 进入审批态之前的业务状态，用于退回恢复 |
| `approvalType` | `ApprovalType?` | 当前审批类型 |

`ApprovalType` 当前包括：

| 枚举值 | 说明 |
| --- | --- |
| `PROPOSE` | 立项或分解方案审批 |
| `ADJUST` | 调整审批 |
| `CANCEL` | 取消审批 |
| `COMPLETE` | 完成审批 |

## 四、进入审批态规则

进入 `PROPOSING`、`ADJUSTING`、`CANCELLING`、`COMPLETING` 时统一写入：

1. `beforeApprovalStatus = 当前业务状态`。
2. `approvalType = 当前审批类型`。
3. `status = 对应审批态`。
4. `currentApproverId` 或 `currentApproverRole` 指向第一审批节点。

各场景示例：

| 场景 | 进入审批前 | 审批态 | `beforeApprovalStatus` | `approvalType` |
| --- | --- | --- | --- | --- |
| 普通事项提交立项 | `DRAFT` | `PROPOSING` | `DRAFT` | `PROPOSE` |
| 公司领导发起待办后部门分解提交 | `PENDING_DECOMPOSE` | `PROPOSING` | `PENDING_DECOMPOSE` | `PROPOSE` |
| 进行中事项申请调整 | `IN_PROGRESS` | `ADJUSTING` | `IN_PROGRESS` | `ADJUST` |
| 进行中事项申请取消 | `IN_PROGRESS` | `CANCELLING` | `IN_PROGRESS` | `CANCEL` |
| 进行中事项提交完成材料 | `IN_PROGRESS` | `COMPLETING` | `IN_PROGRESS` | `COMPLETE` |

## 五、审批通过规则

1. 如果还有下一审批节点，`status` 保持当前审批态，仅切换 `currentApproverId` / `currentApproverRole`。
2. 如果审批结束，则进入目标业务状态，并清空：
   - `beforeApprovalStatus`
   - `approvalType`
   - `currentApproverId`
   - `currentApproverRole`

审批通过后目标状态：

| `approvalType` | 目标业务状态 |
| --- | --- |
| `PROPOSE` | `IN_PROGRESS` |
| `ADJUST` | `IN_PROGRESS` |
| `CANCEL` | `CANCELLED` |
| `COMPLETE` | `COMPLETED` |

## 六、审批退回规则

审批退回时统一执行：

1. `status = beforeApprovalStatus`。
2. `beforeApprovalStatus = null`。
3. `approvalType = null`。
4. `currentApproverId = null`。
5. `currentApproverRole = null`。
6. 写入退回原因和 workflow record。

特别规则：

1. 普通事项 `DRAFT -> PROPOSING`，退回后回 `DRAFT`。
2. 公司领导发起待办 `PENDING_DECOMPOSE -> PROPOSING`，退回后回 `PENDING_DECOMPOSE`。
3. 不使用 `needDecompose` 之类布尔字段解决退回路径，退回路径只以 `beforeApprovalStatus` 为准。

## 七、取消审批中的主要领导节点

重点工作取消不再使用 `PENDING_MAIN_LEADER_CANCEL`。在目标状态机中：

1. 事项保持 `CANCELLING`。
2. `approvalType = CANCEL`。
3. 当前审批节点由 `currentApproverId` / `currentApproverRole` 表示。
4. 当需要公司主要领导审批时，设置 `currentApproverRole = PRESIDENT` 或精确设置 `currentApproverId`。

## 八、历史状态迁移

第六阶段采用清库重建方案 A。以下为旧 15 状态到当前 9 状态的迁移映射：

| 旧状态 | 新状态 |
| --- | --- |
| `DRAFT` | `DRAFT` |
| `PENDING_DEPT` | `PROPOSING` |
| `PENDING_COMPANY` | `PROPOSING` |
| `APPROVED` | `IN_PROGRESS` |
| `IN_PROGRESS` | `IN_PROGRESS` |
| `PENDING_DECOMPOSE` | `PENDING_DECOMPOSE` |
| `PENDING_COMPLETE` | `COMPLETING` |
| `PENDING_EVIDENCE_DEPT` | `COMPLETING` |
| `PENDING_EVIDENCE_COMPANY` | `COMPLETING` |
| `PENDING_MAIN_LEADER_CANCEL` | `CANCELLING` |
| `COMPLETED` | `COMPLETED` |
| `REJECTED` | `DRAFT` |
| `ADJUSTING` | `ADJUSTING` |
| `CANCELLING` | `CANCELLING` |
| `CANCELLED` | `CANCELLED` |

历史实现中的 `pending_dept`、`pending_company`、`approved`、`rejected`、`pending_evidence_dept`、`pending_evidence_company`、`pending_complete` 只作为迁移前兼容状态理解。

**历史退回差异**：旧实现存在 `REJECTED` 状态，退回后进入 `REJECTED`，重新提交再进入审批态。当前架构退回恢复为 `DRAFT` 或 `PENDING_DECOMPOSE`，以审批前记录的状态为准。

**历史完成审批差异**：旧实现中重点/主要工作使用 `PENDING_EVIDENCE_DEPT` / `PENDING_EVIDENCE_COMPANY`，待办事项使用 `PENDING_COMPLETE`。当前统一为 `COMPLETING`。

**迁移数据处理**：旧 `APPROVED` 迁移为 `IN_PROGRESS`，旧 `REJECTED` 迁移为 `DRAFT`（退回原因保留在历史字段和 workflow record 中），旧部门/公司审批中迁移为 `PROPOSING`，旧完成审批中迁移为 `COMPLETING`，旧重点工作主要领导取消审批迁移为 `CANCELLING`。

## 九、字段兼容说明

**已删除的历史字段**（Phase 7）：

| 已删除字段 | 原用途 | 替换为 |
|------------|--------|--------|
| `deptLeaderId` | 部门领导用户关联 | 删除，不引入替代 ID 字段 |
| `deptManagerId` | 部门主管/管理岗用户关联 | 删除，不引入替代 ID 字段 |
| `deptLeaderName` | 部门领导姓名快照 | `responsibleLeader` |
| `deptManagerName` | 部门主管姓名快照 | `responsiblePerson` |
| `supervisor` | 历史文本字段 | `responsiblePerson` |
| `departmentIds` | 多部门 ID 数组 | `responsibleDepartmentIds`（Phase 8B 后亦删除） |

Phase 8B 已删除 `responsibleDepartmentIds`、`cooperateDepartmentIds`、`responsiblePersons`、`cooperatePersons`。当前字段统一为：`departmentId`（唯一主责部门）、`responsibleLeader`（责任领导）、`responsiblePerson`（责任人）、`cooperators`（配合方）。

**历史公司领导查看范围差异**：旧代码曾把 `VICE_PRESIDENT` / `PRESIDENT` 作为公司级角色获得较宽查看范围。当前目标口径：`ADMIN` / `SUPERVISOR` 默认全局查看；`VICE_PRESIDENT` 只查看本人提出、分管、当前审批事项；`PRESIDENT` 至少查看本人提出、当前审批、需主要领导决策事项。

**附件权限差异**：当前附件权限由 `src/lib/attachment-permissions.ts` 管理，部分判断仍依赖标量 `departmentId`、创建人或历史责任字段。目标上应与统一事项查看和办理权限模块对齐。
