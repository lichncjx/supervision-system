## 附件删除异常只读排查

### 1. 缺陷标题

附件删除：服务端或数据结果已生效，但前端请求/刷新链路出现 Failed to fetch 提示。

### 2. 已知复现条件

- 登录用户：dept_manager_a1。
- 页面：事项 C 详情页 /todo/160。
- 操作：删除本人上传的普通附件“手册演示-普通附件-删除示例.pdf”。
- 现象：页面先出现确认框“确定要删除该附件吗？”，确认后附件实际从页面和数据中消失，但页面额外弹出一次 “Failed to fetch”。

### 3. 已确认事实

- 删除前 attachments 中存在两条普通附件记录。
- 删除后只读查询确认“手册演示-普通附件-删除示例.pdf”已不存在。
- 删除后只读查询确认“手册演示-普通附件-保留.pdf”仍存在。
- 事项 C 状态未变化，仍按后续流程进入 completed。
- 前端普通附件删除入口位于 WorkAttachmentPanel，点击后调用详情页的 handleDeleteAttachment。
- handleDeleteAttachment 调用 deleteAttachment 后再执行 onRefresh。
- deleteAttachment 使用 DELETE /api/attachments/{id}，成功响应时不解析响应体；失败响应时读取 JSON 并抛出错误。
- DELETE /api/attachments/{id} 成功路径返回 ok()，即 204 空响应。
- deleteAttachmentUseCase 的顺序是：查附件、校验权限、删除附件记录、删除物理文件、写 operation log、返回成功。

### 4. 最可能的问题位置

最可能位于前端删除请求完成后的请求/刷新链路，具体集中在以下位置：

- src/app/(app)/[type]/[id]/page.tsx 的 handleDeleteAttachment。
- src/features/attachments/client/attachment-api.ts 的 deleteAttachment。
- src/features/works/client/use-work-detail-data.ts 的 onRefresh 后重新拉取详情。
- /api/attachments/[id] DELETE 成功返回 204 后，浏览器侧 fetch 或后续刷新请求可能出现连接中断、开发环境请求失败或未被单独区分的异常提示。

现有代码没有显示出“删除成功后解析 204 空响应导致报错”的直接证据，因为 deleteAttachment 在 res.ok 时不会读取响应体。

### 5. 尚不能确认的部分

- 不能确认 “Failed to fetch” 是 DELETE 请求本身的 fetch reject，还是删除成功后的详情刷新请求失败后被用户误认为删除报错。
- 不能确认服务端是否在删除物理文件或写 operation log 后发生过连接中断。
- 不能确认是否存在开发环境瞬时网络/Next.js dev server 连接问题。
- 需实际抓取浏览器 Network 请求或服务端日志后确认。

### 6. 建议修复方向

- 在浏览器 Network 中区分 DELETE /api/attachments/{id} 与后续 /api/works/{id} 刷新请求的状态。
- 将 handleDeleteAttachment 中的删除请求和刷新请求分别 try/catch，避免删除已成功但刷新失败时弹出“删除失败”类提示。
- deleteAttachment 成功后可先本地乐观移除附件，再异步刷新详情；刷新失败时提示“附件已删除，页面刷新失败，请手动刷新”。
- 服务端可为 DELETE 成功返回明确 JSON，例如 `{ success: true }`，便于前端和调试工具区分成功响应。
- 若确认是文件删除或 operation log 写入导致响应异常，应将数据库记录删除、物理文件删除、日志写入放入更清晰的事务/容错边界。

### 7. 建议优先级

P2，中优先级。

理由：数据结果已生效，不阻断用户完成删除；但错误提示会误导用户，影响正式交付体验和用户信任。

### 8. 是否影响本次用户手册编写

不阻塞第一版手册正文编写。

手册中不应写“删除后会报错但其实已删除”。手册正文只展示删除入口和正常删除语义；该异常作为待修复缺陷单独跟踪。

### 9. 是否阻塞正式上线

建议正式上线前修复。

如果上线前无法修复，应至少补充错误提示兜底，避免用户误判附件未删除或重复操作。
